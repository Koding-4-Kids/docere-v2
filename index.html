Our PR & Review Process

Standard workflow:

1. Pick an issue from GitHub 2. Create a branch: git checkout -b feat/issue-123-description 3. Implement + test locally 4. Push & open PR with description 5. CI runs: linting (ruff), type checking (mypy), tests (pytest) 6. Code review: Youdahe or senior team member - Check logic, ask questions, suggest improvements - Make sure it's documented 7. Address feedback, re-request review 8. CI passes + approval → merge to main 9. Deploy (automatic or manual depending on env)

First PRs may take longer for review. That's expected. We're teaching you our patterns.

Setup & Architecture

Getting from zero to a running tutoring agent

v1 — Simple FastAPI + PostgreSQL (2023)

Single tutoring endpoint, conversation history only

v2 — Async FastAPI + Qdrant + Redis (2024-present)

Memory-augmented learning agent with self-improvement loop

Architecture Comparison

v1: Minimal Stack

FastAPI server ↓ PostgreSQL ↓ Claude API ↓ LMS (Canvas/Moodle)

v2: Full Research Platform

FastAPI (async) ├─ PostgreSQL (relational) ├─ Qdrant (vector embeddings) ├─ Redis (cache + ARQ tasks) └─ Claude API └─ LMS adapters

v2 Request Flow: Detailed

POST /api/v1/chat/conversations/{id}/messages │ ├─ 1. MEMORY ASSEMBLY (async, parallel) │ ├─ Student Profile (PostgreSQL lookup) │ │ └─ engagement_level, concept_mastery, confusion_score │ ├─ Teacher Context (Qdrant similarity search) │ │ └─ top-k course materials matching query │ └─ Interaction History (Qdrant + diversity filter) │ └─ past Q&A pairs with max 0.65 similarity │ ├─ 2. STRATEGY SELECTION (UCB1 bandit) │ ├─ Fetch 5 seed strategies + evolved variants │ ├─ Calculate UCB1 score for each │ └─ Pick highest (or random if exploration phase) │ ├─ 3. PROMPT CONSTRUCTION │ └─ Base tutoring prompt + strategy + memory context (4K token budget) │ ├─ 4. LLM CALL │ └─ Claude generates tutoring response (streaming SSE) │ └─ 5. ASYNC POST-PROCESSING ├─ Embedding generation (Voyage AI) ├─ Memory capture (store in Qdrant + PostgreSQL) ├─ Heuristic scoring (clarity, engagement, quality) └─ Queue verification task (30-300s timeout for student followup)

v2 Setup: Services

Step 1: Clone & start Docker services

$ git clone https://github.com/Koding-4-Kids/docere-v2 $ cd docere-v2 $ docker-compose up postgres redis qdrant -d # Starts 3 services in background: # - postgres:5432 (databases: users, conversations, strategies) # - redis:6379 (cache + ARQ task queue) # - qdrant:6333 (vector DB for memory embeddings)

Wait ~10 seconds for services to be healthy (check logs with docker-compose logs)

v2 Setup: Python Environment

Step 2: Create Python venv & install

$ python3.11 -m venv venv $ source venv/bin/activate $ pip install -e . $ pip install -r dev-requirements.txt # Installs FastAPI, SQLAlchemy 2.0, Qdrant client, # Anthropic SDK, Voyage AI embeddings, pytest, mypy, ruff

Uses Python 3.11+ (async/await, match statements)

Step 3: .env & database migrations

v2 Database Schema (Simplified)

Users ──< Enrollments >── Courses │ ├──< Assignments ──< Submissions │ ├──< CourseMaterials (in Qdrant) │ └──< StudyConfig ──< ResearchEvents │ ├──< Conversations ──< Messages ──< InteractionScores │ │ (helpfulness, clarity, engagement) │ └──< strategy_id ──> Strategies ──< StrategyScores │ (seed + evolved variants) │ ├──< StudentProfiles (engagement_level, confusion_avg) ├──< ConceptMastery (per-concept skill 0.0–1.0) ├──< MemoryRecords (compressed interaction summaries) └──< MemoryRecords → Qdrant (embeddings for semantic search)

v1 vs v2: Technical Deep Dive

Memory System

v1: last N messages from PostgreSQL

v2: 3-source semantic context: student profile + course materials (Qdrant cosine sim) + interaction history (Qdrant + diversity filter, max 0.65 sim)

Strategy Selection

v1: fixed prompt instructions

v2: UCB1 multi-armed bandit: score = avg_score + sqrt(2*ln(total_uses)/strategy_uses)

Outcome Tracking

v1: no scoring

v2: hybrid 2-phase: heuristics (30%) + LLM-as-judge (70%), 4 dimensions weighted (helpfulness 0.35, clarity 0.25, understanding Δ 0.25, engagement 0.15)
